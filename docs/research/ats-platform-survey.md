# recon:ats-platforms

## Summary

I read the adapter contract (internal/services/json.go fetchJSON at :45 / fetchHTML at :96, registerBuiltin at builtin.go:49, multiJobsFunc at :173, multiJobsFuncNamed at :179) and then researched candidates via WebSearch plus GitHub code search, plus reading working open-source adapter implementations fetched from raw.githubusercontent.com. I did NOT live-probe any job board; every endpoint below is corroborated by two or more independent working implementations and/or vendor docs, never by a probe I ran. The single biggest finding is not a new platform at all: internal/services/jibe.go:172 hardcodes `https://%s.jibeapply.com/api/jobs`, but the identical JSON API is served from ~261 employer-owned vanity hosts the repo does not crawl (careers.costco.com, jobs.jcp.com, careers.se.com) — a one-line URL-construction change plus a slug list is worth roughly 175,000 net-new postings with zero new parsing code. Beyond that, the highest employer-coverage-per-effort tier is a set of single-request-per-tenant JSON/XML feeds that carry the whole open-req corpus in one GET: SAP SuccessFactors RMK XML (~107k postings across 744 known tenants at ~144 postings per request — the cheapest enterprise lane I found), Oracle Cloud HCM recruitingCEJobRequisitions (~173k across 1,552 known tenants; crucially the LIST endpoint alone already carries Title/PrimaryLocation/PostedDate, so this repo's four-field JobPosting needs no detail fan-out), Teamtailor /jobs.json, Personio /xml, Recruitee /api/offers/, Pinpoint /postings.json, Breezy /json, Manatal, Crelate RSS and JobScore feed.json. I also recovered externally-verified tenant seed lists totalling ~13,600 slugs across 19 platforms (dated 2026-06/07) and downloaded them to the scratchpad. The hard constraint on all of this is the known crawl timeout: the crawl already fails to finish 1,772 companies in 1h15m, and these additions would add ~9,000 sources and roughly 600k postings, so coverage work must be sequenced behind or alongside throughput work and prioritised strictly by postings-per-HTTP-request. A second constraint is schema: these platforms publish department, employment type, three-state workplace type, posted date, requisition id and structured pay, but internal.JobPosting (internal/job_posting.go:5-22) has only Company/URL/Title/Location/Compensation/Remote *bool, so most of the richness would be discarded on ingest. Key-free is genuinely satisfied for everything I rank in tiers 1-3; Comeet, Fountain and Trakstar/Recruiterbox fail the key-free test and I recommend dropping them. Government sources are weaker than hoped: USAJOBS search requires a (free, instant) key, EURES and UK Civil Service have no confirmed key-free feed, and the best key-free public-sector option is Germany's Bundesagentur für Arbeit REST API.

### Jibe adapter is hardcoded to *.jibeapply.com and misses ~261 vanity-host tenants worth ~175k postings

- files: internal/services/jibe.go, internal/services/builtin.go, internal/services/jibe_test.go, docs/adding-a-source.md

### SAP SuccessFactors RMK: one keyless XML GET returns an entire enterprise's open-req corpus (~144 postings/request)
- impact: critical | effort: medium | confidence: documented
- files: internal/services/successfactors.go, internal/services/adapters_test.go, internal/httpx/httpx.go, docs/source-backlog.md

Endpoint: GET https://career{N}.successfactors.{com|eu}/career?company={companyId}&career_ns=job_listing_summary&resultType=XML . No auth, no cookie, no pagination — a single request returns every open req with the full HTML description inline. Response is <Job-Listing><Job> blocks with <JobTitle> (CDATA), <Job-Description> (CDATA, full HTML), <ReqId>, <Posted-Date> (MM/DD/YYYY, optional), and tenant-variable facet wrappers <filterN>/<mfieldN> each carrying <label>+<value> (location lives in 'Country - Career' or 'Geographic Location' depending on tenant). Apply URL is synthesizable with no extra fetch: https://{host}/career?company={companyId}&career_job_req_id={ReqId}&career_ns=job_application . Two caveats: (a) the feed is NOT strict XML — it emits empty `<>..</>` tags, so a tolerant regex/scanner per <Job> block is required rather than encoding/xml; (b) tenancy is a NON-guessable (companyId, host) pair — companyId is case-sensitive (e.g. nestleHRprdBX) and career5.successfactors.com is NXDOMAIN while career5.successfactors.eu is live. Also strip literal RMK merge tokens like [[salaryMin]]/[[filter1]] that the client-side runtime would have substituted. 744 verified tenant triples (~107,403 postings) at slugs/successfactors_tenants.txt, headed by sap,SAP,career5.successfactors.eu (~1617), capgemini,capgemitecP3,career5.successfactors.eu (~1682), nestle,nestleHRprdBX,career2.successfactors.eu (~1372), exxonmobil,exxonmobilP,career4.successfactors.com (~463). This directly closes the source-backlog.md:42 'SAP SuccessFactors / ExxonMobil' gap.

### Oracle Cloud HCM (ORC): keyless REST list endpoint alone satisfies this repo's JobPosting — no detail fan-out needed
- impact: critical | effort: medium | confidence: documented
- files: internal/services/oraclecloud.go, internal/services/adapters_test.go, internal/httpx/httpx.go, docs/source-backlog.md

GET https://{fa-host}/hcmRestApi/resources/latest/recruitingCEJobRequisitions?onlyData=true&expand=requisitionList.secondaryLocations&finder=findReqs;siteNumber={CX_NNNN},limit={n},offset={k},sortBy=POSTING_DATES_DESC -> {"items":[{"TotalJobsCount":N,"requisitionList":[{Id,Title,PrimaryLocation,PostedDate,JobType,...}]}]}. Zero auth, GET only. Every reference implementation I read pays for a second call to recruitingCEJobRequisitionDetails (?expand=all&onlyData=true&finder=ById;Id="{id}",siteNumber={CX}) purely to get ExternalDescriptionStr/ExternalResponsibilitiesStr/ExternalQualificationsStr — which this repo does not store. So skipping detail makes this ~1 request per 200 postings. Note `finder` must be percent-encoded with `;,=` left safe. 1,552 verified triples (~173,486 postings) at slugs/oracle_orc_tenants.txt, headed by kroger,eluq.fa.us2.oraclecloud.com,CX_2001 (~16,316), autozone,egud.fa.us2.oraclecloud.com,CX_1 (~10,693), albertsons,eofd.fa.us6.oraclecloud.com,CX_1001 (~6,875), macys,ebwh.fa.us2.oraclecloud.com,CX_1001 (~3,158). ### UKG Pro / UltiPro: keyless POST job-board search, ~1,700 live tenants

### Oracle Taleo: keyless POST JSON, but needs a per-tenant portal id and a mandatory tz header
- impact: medium | effort: large | confidence: documented
- files: internal/services/taleo.go, internal/services/adapters_test.go, docs/source-backlog.md

POST https://{tenant}.taleo.net/careersection/rest/jobboard/searchjobs?lang=en&portal={portalId} with body {"multilineEnabled":false,"sortingSelection":{"sortBySelectionParam":"5","ascendingSortingOrder":"false"},"fieldData":{"fields":{},"valid":true},"currentRecordCount":0,"currentPageNo":1,"pageSize":100} -> JSON with a `requisitionList` array and a total count. No API key. There is also a distinct newer Taleo variant ('taleotbe') that is server-rendered HTML at /{instance}/ats/careers/v2/searchResults?org={slug}&cws={cws}, paging 10/row, requiring a JSESSIONID echoed across pages of one walk. ~286 tenants seen in a single Common Crawl snapshot. Closes source-backlog.md:42 (Kaiser Permanente).

### A generic schema.org JobPosting JSON-LD adapter covers many boards with one implementation, but at ~1 request per posting
- impact: medium | effort: large | confidence: documented
- files: internal/services/jsonld.go, internal/services/jazzhr.go, internal/services/workstream.go, internal/services/eightfold.go, docs/source-backlog.md

The vendor-agnostic pattern is: fetch a tenant sitemap (or a server-rendered listing), then fetch each job page and read its <script type="application/ld+json"> JobPosting block for title, description, datePosted, employmentType, hiringOrganization.name, jobLocation.address.{addressLocality,addressRegion,addressCountry}, jobLocationType ("TELECOMMUTE"), identifier.value and, on some boards, baseSalary. Confirmed as the ONLY route for: JazzHR ({slug}.applytojob.com/apply/jobs/ listing -> /apply/jobs/details/{id} pages; 756 verified tenants, ~9,689 postings — salesfocusinc ~233, mra ~203, foxconnggroup ~99, nro, kscourts), Manatal's HTML board, Workstream (www.workstream.us/j/{company_id}/{slug}/positions, ?page=N at 10/page; dead tenants answer 410; a per-IP soft rate limit serves 200s with the JSON-LD STRIPPED, so pace ~1 req/s and re-fetch degraded pages), Eightfold (sitemap at {slug}.eightfold.ai/careers/sitemap.xml pointing at branded careers.* hosts — this SIDESTEPS the PCSX authorization wall recorded at source-backlog.md:65), TalentLyft ({tenant}.talentlyft.com/sitemap.xml), Factorial ({slug}.factorialhr.com/sitemap.xml, but detail pages carry NO JSON-LD — only og:title plus a body slice, so title provenance is weak and the <title> tag is polluted with ' | Company' suffixes), Jobvite detail pages, and Breezy detail pages. Strong recommendation: build this as a shared helper (a jsonld.go beside json.go) rather than as one adapter, and wire it only where no list API exists. Economics are the inverse of tier 1 — roughly one HTTP request per posting versus SuccessFactors' ~144 postings per request — so given the crawl-timeout situation this should be gated behind a per-platform opt-in and probably excluded from the nightly total run.

### Comeet, Fountain and Trakstar/Recruiterbox fail the key-free requirement and should be dropped from the backlog
- impact: low | effort: small | confidence: documented
- files: docs/source-backlog.md

Comeet (now Spark Hire Recruit): https://www.comeet.co/careers-api/2.0/company/{company_uid}/positions?token={company_token}&details=true — the vendor's own developer docs state the company UID forms the URL and the company Token must be added as a `token` query parameter on EVERY request. ### Government and public job banks: honest assessment — mostly key-gated or terms-restricted
- impact: low | effort: medium | confidence: documented
- files: internal/services/arbeitsagentur.go, .github/workflows/track_jobs.yml

USAJOBS: the jobs search endpoint https://data.usajobs.gov/api/search DOES require an Authorization-Key header plus Host and User-Agent headers. The key is free, issued instantly by email, with no approval process, tiering or fee — but it is still a secret, which conflicts with this repo's key-free posture and would need a GitHub Actions secret. Only the /api/codelist/* reference endpoints are truly key-free, and those are taxonomies (pay plans, occupational series, postal codes), not jobs. There is a /api/HistoricJoa endpoint for historic announcements whose auth posture I could not confirm. Germany's Bundesagentur für Arbeit is the strongest key-free public option: https://rest.arbeitsagentur.de/jobboerse/jobsuche-service/pc/v4/app/jobs (search, also /pc/v6/jobs) and /pc/v4/jobdetails/{base64(refnr)} (detail), authenticated by a static, publicly documented X-API-Key of `jobboerse-jobsuche` — effectively key-free, and it is Germany's largest job database; note the agency does not offer this as an *official* API, so it is undocumented-but-open rather than contractually public, and one existing crawler project already ships it as a provider. Canada Job Bank: no open live API; the route is monthly bulk CSV/TSV/JSON/XML dumps on open.canada.ca (dataset ea639e28-c0fc-48bf-b5dd-b8899bd43072), which is snapshot data, not a crawlable feed — usable for the historical trend line in jobs_record.txt but not for a nightly crawl. Its XML feed is partner-gated by application. EURES: I found no key-free public vacancy API despite the ~2M-posting portal; every programmatic route I saw was a third-party scraper. UK Civil Service Jobs / DWP Find a Job: no public API found; DWP publishes a bulk-UPLOAD spec (inbound), not an outbound feed, and Find a Job is being replaced by an experimental service at jobs.service.gov.uk from 30 June 2026. Recommendation: take Arbeitsagentur, treat USAJOBS as a deliberate exception if a secret is acceptable, and drop EURES/UK/Canada from crawl scope.

## Risks

- Coverage and crawl-completion are in direct conflict right now. The nightly Track Jobs run already cannot finish 1,772 companies in 1h15m; the candidate set here is ~13,600 more tenants and roughly 600k net-new postings. Landing even tier 1 before throughput work will push the crawl further past its deadline and make every subsequent snapshot a --allow-partial one, which degrades the trend line rather than improving it.
- jobs_record.txt already faces a coverage step change (13,467 old-scraper postings versus ~473k today). Adding ~600k more creates a second, larger discontinuity. The trend line needs an explicit coverage-generation marker recorded in crawl_report.go before these land, or the graph becomes uninterpretable.
- None of the ~13,600 seed slugs has been verified by this project. They come from a third-party curated repo with dated verification claims (2026-06/07) that I could not re-check, because this container has no outbound access to job boards. Committing them unverified would violate docs/adding-a-source.md:16 and create exactly the permanent-error decay that document warns about. Treat every slug as a candidate until a CI probe confirms it.
- Four platforms return HTTP 200 with vendor-stub content for nonexistent tenants (SmartRecruiters, Zoho Recruit, ApplicantPro, ApplicantStack), so any status-code-based verification will accept garbage and inflate the source count. BrassRing does the opposite and returns HTTP 500 for a wrong partnerid/siteid pair, so a naive health check would classify a mis-transcribed credential as a transient server outage and retry it forever.
- Five of the highest-value platforms have non-guessable composite tenancy — SuccessFactors (companyId + host), Oracle ORC (fa-host + siteNumber), UKG (tenant code + board GUID), BrassRing (partnerid + siteid), Avature (host + section). Tenant discovery is therefore a separate, ongoing research cost that does not scale with the adapter. Budget for it, and design the Source.Key encoding (builtin.go:15-37) to carry multi-part keys before writing the first of these adapters, or every one of them will need reworking.
- Response shapes on these boards drift. Two changes are already documented upstream within the last year: BambooHR moved from flat locationCity/State/Country + boolean isRemote to nested location/atsLocation + nullable isRemote + a locationType discriminator, and Breezy's /json moved from {company,positions} to a flat array with a renamed id and location.city as a string. Adapters must model only the fields they use (docs/adding-a-source.md:127) and tolerate both shapes, or a silent vendor change becomes a silent zero-posting tenant.
- Several of these platforms concentrate enormous tenant counts onto a single host (api.manatal.com 1,601; recruiting.paylocity.com 1,424; workforcenow.adp.com 992; roughly 3 successfactors hosts for 744 tenants). Without servicePolicyFor entries these will produce self-inflicted 429 storms indistinguishable from dead boards, repeating the documented Workable incident at httpx.go:41-44.
- Terms-of-use and robots posture varies and I did not audit robots.txt for any of these hosts. One upstream project records that api.smartrecruiters.com/robots.txt is Disallow: / for all bots except LinkedInBot despite /v1/companies/{tenant}/postings being the documented public read-only API, and that api.ashbyhq.com returns 401 to /robots.txt regardless of user-agent. A conservative robots-respecting crawler would therefore refuse endpoints the vendors publish as public. Whatever policy this project adopts should be decided explicitly and documented, not inherited by accident.
- The Comeet 2.2 endpoint (www.comeet.co/jobs-api/2.2/company/{slug}) appears in one third-party probe table without a token, contradicting Comeet's own developer docs which require a per-company token on every request. I could not resolve that contradiction without a live probe. I have recommended dropping Comeet; if someone wants it, that specific question must be settled in CI first.
- Kroger appears in both the Oracle ORC list (~16,316 postings, JSON) and the Radancy backlog entry (HTML), and several employers appear on both a .jibeapply.com host and a vanity host. Adding both routes would double-count single employers. Any plan landing overlapping platforms needs a posting-level dedup story — the existing Companies() dedup at builtin.go:147-162 works on company name and will not catch this.
- My endpoint and field-name evidence comes from reading third-party open-source implementations and vendor documentation, not from probing the APIs. That is strong for endpoint shape and field names (most are corroborated by two or more independent implementations) but weaker for current liveness and for edge-case behaviour under this project's specific User-Agent and request pattern. Every adapter should ship with its fixture test first and be smoke-tested against 3-5 tenants in CI before its full slug list is committed.
