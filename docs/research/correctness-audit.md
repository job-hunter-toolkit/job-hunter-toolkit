# recon:correctness

## Summary

Adversarial review of the crawler core. I found one bug that alone explains both the nightly timeout and a large silent coverage loss, plus four more confirmed classes of real defect. The headline: `internal/services/workday.go:331` puts `defer resp.Body.Close()` inside the pagination `for` loop, and `httpx`'s `hostLimiter` releases its per-host semaphore slot only on body Close (`httpx.go:370`). With `defaultPerHostLimit = 4`, every Workday tenant reads exactly 4 pages (limit=20 → 80 postings), then blocks on `state.sem <- struct{}{}` until the `http.Client.Timeout` of 2 minutes fires. I proved this by execution: 80 postings, 4 requests, then a 2m0s hard stall ending in "Client.Timeout exceeded while awaiting headers". That is 216 Workday tenants each capped at 80 postings AND each burning 120s of a 32-wide worker slot doing nothing — ~13.5 minutes of pure dead wall-clock in every crawl, and the `health` command never notices because 80 < the 100-posting cap. Second: the peopleforce.io 429s are not merely slow, they are a shared-cooldown livelock — `penalize` pushes a single shared `next` 30s into the future on every 429 while `backoff` independently sleeps another 30s, so all 37 tenants serialize at roughly one request per maxDelay; a scaled measurement (maxDelay 200ms, 10 tenants) took 4.0s for 40 requests, which extrapolates to ~37 minutes of the crawl budget spent producing zero postings. Third: Lever, Jibe, Phenom, Jobvite and Uber terminate pagination only on a short/empty page, so a board that ignores its page parameter loops until the crawl deadline — measured 5,001 requests and 500,001 duplicate postings in 0.8s before I broke out; Jibe even parses `totalCount` and never uses it. Fourth, compensation: the optional `([km])?` magnitude suffix in `moneySinglePattern`/`moneyRangePattern` swallows the first letter of a following word, so "$12,000 monthly" and "$140,000 to $180,000 minimum." both parse to nil, and "$45 knowing the market" yields a fabricated $45,000. Fifth: `periodFromContext` has no day branch even though `PeriodDay` exists with a 260 multiplier, so "$200 per day" is inferred hourly and annualized to $416,000. Non-USD `$` ranges ("C$95,000 - C$120,000") are both mislabelled USD and collapsed to their low end with Max=0. Everything above is CONFIRMED by running code, not by inspection alone. The tests miss all of it for one structural reason: `internal/services/adapters_test.go` stubs a bare `&http.Client{Transport: fixtureTransport}` with no `httpx` layers at all, and `internal/httpx/httpx_test.go:606` explicitly closes response bodies with the comment "Closing the body is what releases the slot" — so no test ever exercises an adapter through the real client. Lower down: `total` derives its "complete"/"partial" status purely from `ctx.Err()` (main.go:451), so a crawl in which hundreds of sources failed still writes a "complete" row into jobs_record.txt; and `internal/companies` (Oxide, Uber) is never registered in `Builtin`, so those adapters have never run in any crawl.

## Findings

### Workday holds every page's response body open, exhausting the per-host limiter after 4 pages and stalling 2 minutes per tenant
- impact: critical | effort: small | confidence: verified-in-code
- files: internal/services/workday.go, internal/httpx/httpx.go, internal/services/adapters_test.go

internal/services/workday.go:331 has `defer resp.Body.Close()` inside the `for {}` pagination loop that starts at line 315, so bodies are closed only when the whole adapter returns. internal/httpx/httpx.go:370 wraps every response body in `releaseOnClose`, whose `release` (returning the per-service semaphore slot acquired at httpx.go:345) fires only on Close. `json.NewDecoder(...).Decode` at workday.go:339 never closes. With `defaultPerHostLimit = 4` (httpx.go:48) and Workday's `limit = 20` (workday.go:312), pages 1-4 permanently consume all 4 slots for that tenant host and page 5 blocks in `case state.sem <- struct{}{}` until the request context ends. VERIFIED BY EXECUTION against a stub transport serving `{"total":1000,...20 postings...}`: postings=80, requests=4, then a hard stall released only by `http.Client{Timeout: 2*time.Minute}` (httpx.go:35) — 'postings=80 requests=4 elapsed=2m0s ... context deadline exceeded (Client.Timeout exceeded while awaiting headers)'. Consequences: (a) all 216 Workday tenants are truncated at 80 postings — for the 4 shared hosts (salesforce.wd12 x3, fedex.wd1 x2, choicehotels.wd5 x2) it is 80 postings shared across those sources; (b) each tenant pins one of the 32 `AllWithConcurrency` slots for 120 seconds doing nothing, i.e. 216*120/32 = ~810s = 13.5 minutes of dead wall clock per crawl; (c) `health` reports these tenants as `ok ... 80 postings` and never hits `healthSampleLimit = 100` (main.go:541), so the truncation is invisible. Tests miss it because adapters_test.go's `fixtureClient` is a bare `&http.Client{Transport: fixtureTransport}` with no hostLimiter, and httpx_test.go:606 always closes bodies. FIX: extract a `workdayPage(ctx, client, cxsURL, offset, limit) (*workdayInfo, error)` helper exactly like `leverPage`/`jibePage`/`phenomPage` already do, so the body is closed per page; independently, make the leak non-silent by logging or bounding slot-hold time in hostLimiter.

### peopleforce.io 429s livelock the crawl: shared cooldown plus independent retry backoff, and a 58-minute Retry-After is retried 4 times anyway
- impact: critical | effort: medium | confidence: verified-in-code
- files: internal/httpx/httpx.go, internal/services/peopleforce.go

servicePolicyFor collapses every `*.peopleforce.io` tenant onto one limiter key `peopleforce.io` with maxConcurrent 2 (httpx.go:263-267). On a 429, `penalize` (httpx.go:325-338) pushes that single shared `next` timestamp to now+min(Retry-After, maxDelay) = now+30s, which every other tenant's `wait` (httpx.go:306-321) then blocks on. Independently, `retryTransport.backoff` (httpx.go:630-632) sleeps another min(Retry-After, maxDelay) = 30s before the next attempt. So each 429 costs the shared service ~30s of frozen throughput AND the individual request ~30s of sleep, and the observed `Retry-After: 3510` is honoured as 30s, meaning we retry a host that asked for an hour, 4 times, and never succeed. VERIFIED BY MEASUREMENT: 10 tenants against an always-429/Retry-After:3510 transport with maxDelay scaled to 200ms took 4.019s for 40 requests — i.e. throughput collapses to ~1 request per maxDelay globally regardless of tenant count. Scaled to the production maxDelay of 30s, the 37 tenants x 4 attempts = 148 requests cost ~37 minutes of crawl wall-clock for zero postings, with each in-flight peopleforce source pinning an `AllWithConcurrency` worker slot the whole time. FIX: circuit-break instead of retrying — when `retryAfter(resp)` exceeds `maxDelay`, stop retrying immediately and mark the service unavailable for the remainder of the crawl (a per-key `unavailableUntil`), so subsequent tenants fail fast with a distinct error rather than queueing; and do not double-charge (either the limiter cooldown or the retry backoff, not both).

### Lever, Jibe, Phenom, Jobvite and Uber paginate forever against a board that ignores its page parameter
- impact: high | effort: medium | confidence: verified-in-code
- files: internal/services/lever.go, internal/services/jibe.go, internal/services/phenom.go, internal/services/jobvite.go, internal/companies/uber.go

Termination is decided solely by page size: lever.go:280 `if len(doc) < limit { break }`, jibe.go:208 `if len(apiResp.Jobs) < jibePageSize { return }`, phenom.go:196 `if len(page.Data.Jobs) < phenomPageSize { return }`, jobvite.go:245 `if found == 0 { return }`, companies/uber.go:92 `if len(doc.Data.Results) == 0 { break }`. None checks a server-reported total and none detects a repeating page. Jibe actually decodes `TotalCount` (jibe.go:119) and never reads it; SmartRecruiters (smart_recruiters.go:152 `offset >= doc.TotalFound`) and Workday (workday.go:364) show the correct pattern. VERIFIED BY EXECUTION with a transport that ignores pagination params and always returns a full page: jibe yielded 500001 postings over 5001 requests in 823ms, lever 500001/5001 in 782ms, phenom 500001/5001 in 876ms — each stopped only because I broke out of the loop. In a real crawl these end only at the crawl deadline, pinning a worker slot and hammering one host for hours. Phenom is the most likely to hit this in practice: it re-requests the *same* search-results page with a different `from`, and reads the server-rendered `eagerLoadRefineSearch` payload; a tenant whose SSR ignores `from` returns identical jobs forever. `Dedupe` hides the symptom in `total` (the count stays right) while the time is still burned; `postings --no-dedupe` would emit duplicates without end. FIX: for Jibe use the already-decoded `totalCount`; for Lever/Phenom/Jobvite add a repeat guard (hash the page's first posting URL, or track a seen-ID set per source, and stop when a page introduces no new IDs) plus a hard page cap.

### Money regex magnitude suffix eats the following word's first letter, silently destroying valid pay ranges
- impact: high | effort: small | confidence: verified-in-code
- files: internal/compensation_text.go, internal/compensation_text_test.go

`moneySinglePattern` (compensation_text.go:155-157) and `moneyRangePattern` (compensation_text.go:150-152) both end in `\s*([km])?`, which is unanchored, so the `k`/`m` of the *next word* is consumed as a magnitude suffix and `parseMoney` (compensation_text.go:351-356) multiplies by 1e3 or 1e6. The inflated value then fails the `maxPlausibleAnnual = 3_000_000` check in `buildCompensation` (compensation_text.go:273) and the whole posting silently reports no pay — the exact 'broken source becomes silently empty' failure class this project already has a history of. VERIFIED BY EXECUTION: `Salary: $12,000 monthly` -> nil (correct answer is 144,000/yr; `Salary: $12,000 per month` -> 144,000 confirms the parser is otherwise fine); `The salary for this role is $95,000 maximum.` -> nil; `Base pay of $85,000 minimum for this role.` -> nil; `The pay range for this role is $140,000 to $180,000 minimum.` -> nil (an entire explicit range destroyed). The x1000 case can also fabricate a plausible wrong number rather than dropping it: `The salary is $45 knowing the market.` -> min=45000 USD. Existing tests (compensation_text_test.go) only use fixtures where the figure is followed by punctuation or a non-k/m word. FIX (RE2-safe, no lookahead available): change the suffix group to `([km])?\b` in both patterns, or keep the group and post-validate that the byte after the suffix is not a letter before applying the multiplier; add table cases for 'monthly', 'minimum', 'maximum', 'million'.

### Day rates are annualized as hourly, overstating pay by 8x
- impact: high | effort: small | confidence: verified-in-code
- files: internal/compensation_text.go, internal/job_posting.go

`periodFromContext` (compensation_text.go:316-342) has branches for hour, week, month and year but none for day, so it returns `PeriodUnknown` for a day rate. `Compensation.effectivePeriod` (job_posting.go:87-102) then applies `hourlyMagnitudeCeiling = 250` (job_posting.go:53) and calls any figure <= 250 hourly, multiplying by 2080 (job_posting.go:43). `PeriodDay` and its 260 multiplier exist (job_posting.go:31, 45) and are reachable from the Lever and Jibe API adapters (lever.go:297, jibe.go:125) but are unreachable from prose. VERIFIED BY EXECUTION: `This role pays $200 per day.` -> min=200 period="" annualMax=416000; `The pay rate for this role is $200 - $240 per day.` -> annualMin=416000 annualMax=499200. A genuine $200/day contract role (~$52,000/yr at 260 days) is published as a $416,000 job, which corrupts `--min-pay` and any downstream pay comparison, and it is emitted with Provenance 'description' so a consumer that trusts the provenance ladder still gets a number that is wrong by 8x. Larger day rates ($600/day) currently escape only by accident: they exceed the ceiling, are inferred annual, and are then rejected as below `minPlausibleAnnual`, so those postings report no pay at all. FIX: add `if strings.Contains(window, "per day") || strings.Contains(window, "daily") || strings.Contains(window, "/day") || strings.Contains(window, "a day") || strings.Contains(window, "per diem") { return PeriodDay }` before the hourly checks in periodFromContext.

### Non-USD dollar ranges are labelled USD and silently collapse to their lower bound
- impact: high | effort: medium | confidence: verified-in-code
- files: internal/compensation_text.go, internal/filter.go, internal/job_posting.go

Two defects compound. (1) `buildCompensation` hardcodes `Currency: "USD"` (compensation_text.go:267) for anything the `$` pattern matched, but `$` is also CAD, AUD, NZD, SGD, HKD and MXN. (2) `moneyRangePattern` (compensation_text.go:151) makes the second currency marker `(?:\$|usd\s*)?` optional but requires digits immediately after it, so a currency-prefixed second operand like `C$120,000` fails to match the range; the text then falls through to `moneySinglePattern`, which matches only the first figure. VERIFIED BY EXECUTION: `The salary range for this position is C$95,000 - C$120,000.` -> min=95000 max=0 cur=USD (the 120,000 is lost and 95,000 is presented as the whole range); `Salary range: A$110,000 - A$140,000 per year` -> min=110000 max=0 cur=USD; `Salary: $150,000 USD - EUR140,000` -> min=150000 max=0. Downstream, `Filter.MinAnnual` (filter.go:118-123) compares `AnnualMax()` (job_posting.go:109-120) as a bare float with no currency conversion or currency check anywhere in the codebase, so `--min-pay 200000` will match a posting whose employer-published range is 8,000,000 JPY (from Lever/Jibe/Ashby structured fields, which do carry a real currency code). FIX: (a) capture the currency prefix (`C$`, `A$`, `NZ$`, `S$`, `HK$`, `MX$`, `USD`, `CAD`, ...) as a group and set Currency from it, refusing the match when the two ends disagree; (b) make MinAnnual either currency-aware or explicitly restrict it to a single currency and document that.

### PeopleForce silently returns only page 1 whenever the 'Displaying X - Y of Z' string is missing
- impact: medium | effort: small | confidence: verified-in-code
- files: internal/services/peopleforce.go, internal/services/peopleforce_test.go

peopleforce.go:185: `if !totalFound || runningCount >= totalCount { break }`. `totalFound` comes from `extractTotalCount` (peopleforce.go:196-230), which requires the regex `Displaying\s+\d+\s*-\s*\d+\s+of\s+(\d+)` to match inside a `<p>` or `<div>`. If PeopleForce changes that wording, renders the count in a `<span>`, localises it, or omits it for small boards, `totalFound` stays false and the loop breaks after the first page — reporting a plausible non-zero count rather than an error, so `health` marks the source `ok` and nobody sees the truncation. This is the same silent-truncation shape as the documented filter-applied-twice incident. The peopleforce_test.go file is 116 bytes (a live-network gate only), so there is no fixture exercising the two-page path at all. FIX: treat a missing total as 'keep paginating until an empty page' rather than 'stop', i.e. only use totalCount as an early exit, never as the sole permission to continue; add a hermetic two-page fixture with and without the Displaying string.

### `total` reports status "complete" no matter how many sources failed, and the workflow records that row as a real data point
- impact: medium | effort: small | confidence: verified-in-code
- files: main.go, crawl_report.go, .github/workflows/track_jobs.yml

main.go:451-455 computes `truncated := ctx.Err() != nil` and derives status purely from it. The `failed` counter incremented at main.go:437-439 is logged (main.go:476) but never influences the status, never reaches the row written at main.go:482-483, and never reaches `crawlManifest.Status` (crawl_report.go:49). The manifest does carry `source_counts` from `SourceRun.Status` (crawl_report.go:38-40), but .github/workflows/track_jobs.yml only gates on `POSTINGS -ge 1000` and `STATUS in {complete, partial}` before `cat total.txt >> jobs_record.txt`. Concrete failure: with the Workday body-leak bug above, all 216 Workday sources error out after 80 postings each; if the rest of the crawl finishes inside 350m, the run records `complete` with ~17k Workday postings instead of the true figure, and that point becomes a permanent part of the trend line indistinguishable from a healthy observation. Same for an IP-level block on a single large platform. FIX: make `status` a function of the failure ratio as well as the deadline — e.g. emit `degraded` (and refuse to record without an explicit flag) when `source_counts.failed + source_counts.truncated` exceeds a threshold, or when the posting total deviates from the previous recorded point by more than a set percentage; surface `failed` in the manifest as a top-level field.

### internal/companies adapters (Oxide, Uber) are never registered, so they have never run in any crawl
- impact: medium | effort: small | confidence: verified-in-code
- files: internal/companies/uber.go, internal/companies/oxide.go, internal/services/builtin.go

`registerBuiltin` is called from an `init()` in every file under internal/services/ (13 platforms) but from nothing under internal/companies/. Grep for `registerBuiltin` across internal/companies/*.go returns nothing, and main.go never imports the companies package. `services.Builtin` (builtin.go:45) is therefore the whole crawl, and `Oxide` and `Uber` are dead code that `companies`, `total` and `health` can never reach. Both also have their own defects that would surface the moment they are wired in: companies/uber.go:81-83 and :88-90 discard the HTTP error and the decode error with a bare `return` and no yield (a broken Uber board would report as 'not hiring'); companies/uber.go:84 repeats the Workday `defer resp.Body.Close()`-inside-the-loop bug; and `Uber` has the non-standard signature `(iter.Seq[*JobPosting], error)` rather than `internal.JobsFunc`, so it cannot be registered without adaptation. FIX: either register them behind a `companies` platform with the error paths fixed and the defer hoisted into a per-page helper, or delete them so the source count is honest.

### "up to $X" is recorded as the range minimum with Max=0
- impact: low | effort: small | confidence: verified-in-code
- files: internal/compensation_text.go, main.go

`ParseCompensationFromText` falls through to `moneySinglePattern` for open-ended phrasing and `buildCompensation(value, 0, ...)` (compensation_text.go:232) assigns it to `Min`, leaving `Max` zero. VERIFIED BY EXECUTION: `Salary up to $200,000 depending on experience.` -> min=200000 max=0. The CSV writer then emits pay_min=200000 with an empty pay_max (main.go:294-298) and `describeCompensation` falls to its default branch and prints the Min (main.go:760-761), so a stated ceiling is published as a floor. `AnnualMax()` uses `max(Min, Max)` so `--min-pay` happens to behave, but any consumer reading the JSON `min` field is misled. The same shape applies to the C$/A$ collapse in the currency finding, which produces a genuine low bound stored as though it were the only figure. FIX: detect the open-ended cue ('up to', 'as much as', 'maximum of') in the pre-figure window and assign to Max rather than Min; symmetrically, 'starting at'/'from' should assign to Min.

### newPostingPrinter dereferences the posting without a nil check, unlike every other consumer
- impact: low | effort: small | confidence: verified-in-code
- files: main.go

main.go:292 (`j.Compensation.IsZero()`) and main.go:321/325 dereference `j` unconditionally. `Dedupe` (filter.go:249-251) and `Filter.Match` (filter.go:106-108) both explicitly guard against a nil posting, so the printer is the only unguarded consumer. Today the path is unreachable — every adapter yields either a non-nil posting or a non-nil error, and `AllWithConcurrency`'s terminal `yield(nil, err)` (all.go:143) always has a non-nil error — but `postings --no-dedupe` with no filter flags passes the iterator straight to `emit` (Filter.Apply short-circuits at filter.go:160 when IsZero), so the first adapter that ever yields `(nil, nil)` panics the command rather than skipping a row. This is a one-line hardening against a whole class of future adapter bug, in a codebase that explicitly recovers from adapter panics elsewhere (all.go:111, main.go:687). FIX: `if j == nil { return nil }` at the top of each emit closure.

### Compensation cue/period windows slice a lowercased string with byte offsets taken from the original
- impact: low | effort: small | confidence: inferred
- files: internal/compensation_text.go, internal/compensation_markup.go

`isPayContext` (compensation_text.go:286-289) and `periodFromContext` (compensation_text.go:317) index `lowered` (built at compensation_text.go:198 via `strings.ToLower(normalized)`) using match offsets computed against `normalized`. `compensation_markup.go:152-168` does the same with `parseMoneyRangeIn`. `strings.ToLower` is not length-preserving for all inputs — U+0130 grows 2 bytes to 3, U+212A KELVIN SIGN shrinks 3 bytes to 1 — so any description containing such runes before the money figure shifts the cue and period windows, which can flip a pay figure from accepted to rejected or change its inferred period. Common Latin-1 accented uppercase is length-preserving, so the practical blast radius is small, and a slice-bounds panic would need ~70 shrinking runes before the figure and would be recovered by all.go:111 anyway. I did not construct a failing input, so this is INFERRED, not confirmed. FIX: lowercase once and derive the match offsets from the same string (run the regexes against `lowered` with `(?i)` already present, or keep a rune-index map).

### Dedupe memory is linear and currently ~59 MB — not a leak, but sized here for the record
- impact: low | effort: small | confidence: verified-in-code
- files: internal/filter.go, main.go

`Dedupe` (filter.go:237-271) retains the full URL string of every posting in `seen` for the whole crawl. MEASURED with 473,385 realistic Greenhouse-shaped URLs: heap grew 58.8 MB (0.3 -> 59.2 MB), i.e. ~124 bytes per posting. That is fine on a GitHub runner today and would be ~125 MB at 1M postings. Correctness is sound: URL is the key, the `Company\x00Title\x00Location` fallback at filter.go:257 is well-formed, errors bypass dedup, and nil postings are skipped. The only latent issue is that `Dedupe` is applied before the filter in `postings` (main.go:183-186) and is the sole nil-posting guard for `total` (main.go:442 dereferences `jobPosting.Company` with no check of its own). No change needed now; if memory ever matters, key on a 64-bit hash and accept the collision risk, or reset per-source (which would stop cross-ATS dedup, the stated purpose).

## Recommended plan

1. Fix the Workday body leak first — it is the single highest-value change. Extract `workdayPage(ctx, httpClient, cxsURL, offset, limit) (*workdayInfo, error)` mirroring the existing `leverPage` (lever.go:218) and `jibePage` (jibe.go:154) helpers, move the request/decode/`defer resp.Body.Close()` into it, and call it from the loop in `Workday`. Nothing else in workday.go changes.
   rationale: Restores full pagination for 216 Workday tenants (currently hard-capped at 80 postings each) and removes ~13.5 minutes of dead wall-clock from every crawl. Confirmed by execution: postings=80, requests=4, 2m0s stall.
   files: internal/services/workday.go

2. Add a hermetic regression test that runs an adapter through the REAL client: `httpx.NewClient(httpx.WithTransport(stub))` where the stub serves a paginated Workday response claiming total=1000, with a short context. Assert the adapter reads all 1000 postings and issues 50 requests. Put the same shape in internal/httpx as a `TestPerHostLimitSlotIsNotLeakedByAdapters`.
   rationale: The entire adapter suite stubs a bare `&http.Client{Transport: fixtureTransport}` (adapters_test.go `fixtureClient`) and httpx_test.go:606 always closes bodies, so no existing test can ever see a slot leak. Without this test the bug regresses the next time someone adds a paginating adapter.
   files: internal/services/adapters_test.go, internal/httpx/httpx_test.go

3. Circuit-break services that ask for a cooldown longer than maxDelay. In `hostLimiter`, add a per-key `unavailableUntil time.Time`; when `retryAfter(resp)` exceeds `h.maxDelay`, set it and have `RoundTrip` fail fast with a typed error for the rest of that window. In `retryTransport.RoundTrip`, stop retrying (do not sleep, do not re-attempt) when Retry-After exceeds maxDelay.
   rationale: peopleforce.io returns Retry-After 3510s; today that is clamped to 30s and retried 4 times per tenant while `penalize` freezes the shared `next` for all 37 tenants. Measured: throughput collapses to ~1 request per maxDelay globally, which extrapolates to ~37 minutes of crawl budget for zero postings. Failing fast turns a 37-minute stall into 37 immediate, correctly-attributed errors.
   files: internal/httpx/httpx.go

4. Bound pagination in the five unguarded adapters. Use the server-reported total where one exists (Jibe already decodes `totalCount` at jibe.go:119 and ignores it). Where none exists (Lever, Phenom, Jobvite), add a repeat guard: keep a per-source set of yielded URLs and stop when a page contributes zero new ones, plus a hard page ceiling.
   rationale: Measured against a page-repeating stub: jibe/lever/phenom each issued 5,001 requests and yielded 500,001 postings in under a second, stopping only because the consumer broke. In production such a tenant pins a worker slot and hammers one host until the crawl deadline.
   files: internal/services/jibe.go, internal/services/lever.go, internal/services/phenom.go, internal/services/jobvite.go

5. Fix the money regex suffix: change `([km])?` to `([km])?\b` in both `moneyRangePattern` (compensation_text.go:151) and `moneySinglePattern` (compensation_text.go:156). Add table cases for '$12,000 monthly', '$95,000 maximum', '$140,000 to $180,000 minimum.', '$45 knowing'.
   rationale: Confirmed: the unanchored suffix consumes the next word's leading k/m, multiplies by 1e3/1e6, and the inflated value is then silently rejected by the plausibility bound — three valid ranges parsed to nil and one fabricated $45,000. Go's RE2 has no lookahead, so `\b` is the available anchor.
   files: internal/compensation_text.go, internal/compensation_text_test.go

6. Add a day branch to `periodFromContext` (before the hourly checks) returning `PeriodDay` for 'per day', 'daily', '/day', 'a day', 'per diem'.
   rationale: `PeriodDay` and its 260 multiplier already exist and are used by the Lever/Jibe API paths, but prose can never produce it, so `$200 per day` falls into the `hourlyMagnitudeCeiling <= 250` branch and is published as $416,000/yr — an 8x wrong number, confirmed by execution.
   files: internal/compensation_text.go

7. Make currency explicit rather than assumed. Capture the currency marker as a regex group (C$, A$, NZ$, S$, HK$, MX$, USD, CAD, ...), set `Compensation.Currency` from it, and reject a range whose two ends carry different markers. Separately decide what `Filter.MinAnnual` means across currencies — either convert, or restrict it to a single currency and document that.
   rationale: Confirmed: 'C$95,000 - C$120,000' becomes USD min=95,000 max=0 — mislabelled currency AND the upper bound silently dropped, because the second operand's `C` breaks the range match and the text falls through to the single-figure pattern. MinAnnual then compares raw floats against employer-published JPY/INR ranges from the Ashby/Lever/Jibe adapters with no conversion.
   files: internal/compensation_text.go, internal/filter.go

8. Make the crawl's completeness verdict depend on source outcomes, not only on the deadline. Add a `failed` (and `truncated`) top-level field to `crawlManifest`, and have `total` emit a third status (e.g. `degraded`) when the failed+truncated share of sources exceeds a threshold; teach track_jobs.yml to refuse to append a degraded row without an explicit opt-in, the way it already handles `partial`.
   rationale: `truncated := ctx.Err() != nil` (main.go:451) is the only input to status, so a crawl that finished on time with 216 dead Workday sources still writes `complete` into jobs_record.txt and permanently corrupts the trend line. The workflow's only other guard is POSTINGS >= 1000.

## Risks

- The Workday fix will roughly multiply Workday's contribution to the posting count (216 tenants currently truncated at 80 postings each, some of which publish tens of thousands). The next recorded jobs_record.txt point will jump sharply for a reason unrelated to the labour market — a second coverage step change on top of the known old-scraper one. Land it with a manifest diff and annotate the chart, or the trend line becomes uninterpretable.
- The same fix makes the crawl do vastly more work: FedEx alone is documented at 138,000+ postings at 20 per page (~6,900 sequential requests, throttled to 4 concurrent per tenant host). Fixing the leak without also raising Workday's page `limit` or adding a per-source posting ceiling may turn a 13.5-minute stall into a much longer legitimate crawl and still miss the 350m budget. Measure a single large tenant before assuming the timeout is solved.
- The pagination repeat-guards add a per-source seen-set on top of the global Dedupe map (measured at ~124 bytes/posting), so memory rises. Scope the guard to page-level identity (hash of the page's posting IDs) rather than retaining every URL per source.

Any downstream consumer or saved query using --min-pay will see different results. The `Provenance` field already exists to communicate this; consider bumping the crawl manifest schema version when parser semantics change.
- The peopleforce circuit-breaker converts a slow-but-eventually-attempted source into a fast failure. Those 37 tenants will flip from 'ok/empty' to 'failed' in health reports, which is more honest but will look like a regression in the source_counts table unless it is called out.
