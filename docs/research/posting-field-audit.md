# recon:data-richness

## Summary

The crawler decodes 4–6 fields per posting (`Company/URL/Title/Location` + optional `Compensation`/`Remote`, internal/job_posting.go:5-22) while the responses it already downloads carry far more. Three distinct classes of loss exist. (1) Fields that are *decoded into Go structs and then never read*: BambooHR's `departmentLabel`/`employmentStatusLabel`/`isRemote`/`locationType`/`atsLocation` (internal/services/bamboohr.go:80-94), Workday's `postedOn`/`bulletFields`/`facets` (internal/services/workday.go:283-294), Rippling's `department.name`/`workplaceType`/`language`/`countryCode`/`stateCode` (internal/services/rippling.go:161-173), Workable's `countryCode` (internal/services/workable.go:94). These are zero-request, zero-byte, zero-risk wins available today. (2) Fields that are *commented out in the struct* — i.e. the author saw them in a real response and deliberately excluded them: Greenhouse `updated_at`/`requisition_id`/`internal_job_id`/`metadata` (greenhouse.go:671-692), Lever `categories.{commitment,department,level,team}`/`createdAt`/`description`/`descriptionPlain`/`applyUrl` (lever.go:183-212), and Uber's enormous set including recruiter and hiring-manager identity (companies/uber.go:20-50). (3) Fields present in the response but never modelled: Ashby's `department`/`team`/`employmentType`/`workplaceType`/`publishedAt`/`descriptionHtml`/`descriptionPlain`, SmartRecruiters' `releasedDate`/`typeOfEmployment`/`experienceLevel`/`function`/`industry`/`customField`, Gem's whole extra field set. On compensation: description prose is **free** (already on the wire, request count unchanged) on Ashby, Lever, and Uber; **free in request count but 13.7x in bytes** on Greenhouse via `?content=true` on the same list URL; and **1 extra request per posting** on Workday (~20x, page size 20), SmartRecruiters, BambooHR, Rippling, Phenom, Jobvite, and PeopleForce. Ashby alone is 418 sources whose descriptions are downloaded and thrown away by the JSON decoder today. I also verified a live data-loss bug: the Gem adapter builds every URL from `item.ExtID`, but its own GraphQL query never selects `extId` (gem.go:146 vs gem.go:166), so all postings for a company share one URL and `internal.Dedupe` (filter.go:253) collapses them — measured 3 postings in, 1 out. The extension is backward compatible if every new JSON field carries `omitempty`/`omitzero` and the CSV column set stays frozen at 8 by default behind an opt-in `--csv-columns`. The one dangerous integration point for new filters is `Filter.IsZero` (filter.go:147-155): `Apply` short-circuits on it, so a new field not added there makes the new flag silently match everything.

## Findings

### Ashby: the full job description and 8 other fields are already downloaded and discarded by the decoder (418 sources)
- impact: critical | effort: small | confidence: documented
- files: internal/services/ashbyhq.go

Endpoint fetched today: `https://api.ashbyhq.com/posting-api/job-board/<slug>?includeCompensation=true` (internal/services/ashbyhq.go:492). The modelled struct (ashbyhq.go:436-465) decodes only `jobUrl`, `title`, `location`, `isRemote`, and the `compensation` subtree. The same response body documented by Ashby and by third-party integrators also contains: `id`, `department`, `team`, `employmentType` (e.g. "FullTime"), `workplaceType` (e.g. "Remote"), `publishedAt` (ISO-8601, e.g. "2021-04-30T16:21:55.393+00:00"), `isListed`, `applyUrl`, `secondaryLocations`, `address` (parsed postalAddress parts), `shouldDisplayCompensationOnJobPostings`, and critically **`descriptionHtml` and `descriptionPlain`** — the full posting body. Because encoding/json silently drops unknown keys, these bytes are already paid for on every one of the 418 Ashby sources and thrown away. Adding them costs 0 extra requests and 0 extra bytes. This is the single largest free win in the repo and it also makes prose pay-extraction free for Ashby.

### Gem: every posting URL is wrong because the adapter's own GraphQL query never selects extId — dedupe collapses each company to a single posting
- impact: critical | effort: small | confidence: verified-in-code
- files: internal/services/gem.go, internal/filter.go

gem.go:146 sends `query JobPostingInfo($boardId: String!) { oatsExternalJobPostings(boardId: $boardId) { jobPostings { id title companyUrl locations { name city isoCountry } } } }` — no `extId`. gem.go:166 then builds `url := fmt.Sprintf("https://jobs.gem.com/%s/%s", company, item.ExtID)` where `ExtID` (gem.go:77, tag `extId`) is therefore always empty. I verified this by running the adapter through a stub transport with a response containing exactly the fields the query selects: every posting came back as `url="https://jobs.gem.com/bluesky/"`. Because internal.Dedupe keys on `job.URL` (filter.go:253), a second run through Dedupe went from 3 postings in to 1 posting out. Across 51 Gem sources this caps Gem's entire contribution at ~51 postings. Fix by selecting `extId` in the query (it is already modelled). While editing that one string, the same single POST can also return `descriptionHtml`, `firstPublishedTsSec`, `job{employmentType,requisitionId,locationType,department{name}}` and `locations{isRemote}` — all already modelled at gem.go:76-111 but never requested. Gem is the cheapest platform in the repo to enrich: one string edit, zero extra requests. The location join at gem.go:175 also emits "Remote, , US" when city is empty.

### Backward-compatible JobPosting extension: every new JSON field must be omitempty/omitzero, and the four core names must stay non-omitempty
- impact: critical | effort: medium | confidence: verified-in-code
- files: internal/job_posting.go, internal/services/observe.go, internal/services/builtin.go

Today internal/job_posting.go:6-9 emits `company`, `url`, `title`, `location` unconditionally (no omitempty) and `compensation`/`remote` with omitempty (:15,:21). Rule: never add omitempty to the four core fields — a consumer doing `.location` on NDJSON would start seeing `null`. Every new field gets `,omitempty` (strings, slices) or `,omitzero` (time.Time, structs); go.mod is at go 1.25.0 and `omitzero` is already house style at internal/services/observe.go:36-38. With that, a posting carrying no enrichment marshals to byte-identical JSON to today, which should be locked down with a golden test. Proposed additions, all omitempty: `department`, `team`, `employment_type`, `workplace_type`, `seniority`, `function`, `industry`, `office`, `city`, `region`, `country` (ISO-3166 alpha-2 where the board supplies a code), `locations` ([]string for secondary/all-locations), `posted_at`/`updated_at`/`closes_at` (time.Time + omitzero), `requisition_id`, `external_id` (the ATS's own posting id), `language`, `description` (normalised plain text), `description_html`, and a `source` object carrying platform + tenant key (Source.Platform/Key already exist at internal/services/builtin.go:18-23 but never reach a posting). Employment type and workplace type should be closed string enum types (`EmploymentType`, `WorkplaceType`) with `""` as the zero value so omitempty works and so each adapter normalises its own vocabulary (`FullTime` / `Full Time Position` / `full-time` / `commitment: Fulltime`) exactly once, at the adapter boundary — never at filter time.

### CSV backward compatibility: the 8-column order is asserted by an exact-length test, so richer columns must be opt-in and headerless-by-default must survive
- impact: high | effort: small | confidence: verified-in-code
- files: main.go, main_test.go

main.go:305 writes exactly `[]string{Company, Title, Location, URL, payMin, payMax, currency, period}` and main.go:229 documents the format as headerless. main_test.go:599-601 asserts both the values and `len(records[0]) == 8` exactly, so unconditionally appending columns is a breaking change to a committed contract, not just a test edit. Recommended story: (1) default `--csv` stays exactly those 8 columns forever, appended-only if ever changed; (2) add `--csv-columns=core|extended|<explicit,comma,list>` where `core` is the default 8, `extended` is the 8 plus a frozen documented tail, and an explicit list is emitted in the order given; (3) add `--csv-header` defaulting to **false**, because emitting a header by default would make every existing pipeline read row 1 as a posting; (4) when `--csv-columns` is passed with a non-`core` value, default `--csv-header` to true (an unfamiliar column set is unusable unnamed) while still honouring an explicit `--csv-header=false`. Keep the human text format (main.go:319-329) unchanged by default for the same reason — it is a de-facto parseable format.

### Opt-in design for descriptions: a three-tier mode, not a boolean, plus explicit plumbing of per-crawl options
- impact: critical | effort: medium | confidence: verified-in-code
- files: docs/compensation.md, internal/compensation_text.go, internal/compensation_markup.go, .github/workflows/track_jobs.yml

docs/compensation.md:88-91 states the blocker precisely: 'it belongs behind an opt-in flag rather than on by default, which needs the adapter signature to carry per-crawl options. That is the next step; it was left undone rather than bolted on as hidden global state.' Proposal — Tier 0 `free` (default ON): decode what is already on the wire and run internal.ParseCompensationFromDescription on Ashby/Lever/Uber/Gem bodies inline, guarding with Compensation.MoreTrustedThan (compensation_text.go:46-56) so a prose figure can never overwrite an employer field; then **discard the description text unless the user asked to keep it**, since 473k postings x a few KB is gigabytes of stdout. Tier 1 `--descriptions=same-request`: sets `?content=true` on Greenhouse (also yielding departments+offices) and adds descriptionHtml to the Gem query; request count unchanged, Greenhouse bytes 13.7x. Tier 2 `--descriptions=detail[=platform,platform]`: per-posting fetches, off by default, per-platform allowlisted, with its own budget (`--detail-limit=N` postings and a separate detail timeout) and never enabled in .github/workflows/track_jobs.yml. A single boolean is the wrong shape because it hides the fact that 'on' means 13.7x for Greenhouse, 1.0x for Ashby, and 20x for Workday.

### Options plumbing: exactly seven signatures and three call sites need to change; a context value would reintroduce the hidden state the docs rejected
- impact: high | effort: medium | confidence: verified-in-code
- files: internal/all.go, internal/services/builtin.go, internal/services/observe.go, main.go, docs/compensation.md

The chain that must carry an `internal.Options` value: `internal.JobsFunc` (internal/all.go:20), `internal.All`/`AllWithConcurrency` (all.go:35,:42), `services.Source.Jobs` (builtin.go:36), `services.companyJobsFunc` (builtin.go:165), `multiJobsFunc`/`multiJobsFuncNamed` (builtin.go:173,:179), and the wrapper returned by `observeSource` (observe.go:88). Call sites: main.go:180 (postings), main.go:421-427 (total), main.go:695 (health). Each of the 13 service adapters plus the 2 company adapters gains an `opts internal.Options` parameter. This is mechanical and compiler-checked. ### New filter flags: Filter.IsZero is the trap — Apply short-circuits on it, so a field missing there makes the new flag match everything
- impact: high | effort: medium | confidence: verified-in-code
- files: internal/filter.go, main.go

internal/filter.go:159-162: `Apply` returns `jobs` unchanged when `f.IsZero()`. `IsZero` (filter.go:147-155) enumerates its fields by hand. Any new field added to `Filter` (filter.go:18-46) but forgotten in `IsZero` means `--department engineering` on its own silently returns the entire crawl. Recommended guard: a reflection-based test that walks `Filter`'s fields and fails when a non-zero value for any single field does not make `IsZero()` false — this converts a silent data-correctness bug into a test failure. Proposed flags, honouring OR-within/AND-across (filter.go:14-17): `--department`, `--team`, `--function`, `--industry`, `--seniority`, `--language` as `[]string` using the existing `matchesAny` substring semantics (filter.go:191-197, which correctly treats an all-blank list as 'no constraint'). `--employment-type` and `--workplace-type` should deviate deliberately: match by **equality against the normalised enum**, not substring, because 'contract' would otherwise match 'contractor' and 'part' would match nothing predictable; reject unknown values at flag-parse time with a message listing the valid set. `--posted-since`/`--posted-before`/`--updated-since` take either an RFC3339 date or a Go duration; postings with no date must be **excluded**, following the precedent MinAnnual already sets and documents at filter.go:38-45, and the flag help must say so. `--country` should prefer exact ISO-3166 match on the new field and fall back to substring on Location. `--has-description` mirrors `--has-pay`. Two existing pieces become usable for free: `JobPosting.IsHybrid()` (filter.go:95-102) is written but never called by `Match`, and `--workplace-type=remote` should prefer the structured field then fall back to `IsRemote()` (filter.go:70-90) so the existing `--remote` flag keeps its current heuristic behaviour unchanged.

### Adapters must normalise vocabulary at the adapter boundary, or every filter becomes a per-platform special case
- impact: high | effort: medium | confidence: verified-in-code
- files: internal/services/ashbyhq.go, internal/services/lever.go, internal/services/bamboohr.go, internal/services/rippling.go, internal/services/gem.go, internal/services/workday.go, internal/filter.go

The same concept is spelled differently on every platform: employment type is Ashby `employmentType: "FullTime"`, Lever `categories.commitment: "Fulltime"` (lever.go:186), BambooHR `employmentStatusLabel` (bamboohr.go:82), SmartRecruiters `typeOfEmployment.label`, PeopleForce the literal string 'Full Time Position' (peopleforce.go:114), Gem `job.employmentType` (gem.go:95), Phenom `type`. Workplace type is Ashby `workplaceType`, Lever `workplaceType`, Rippling `locations[].workplaceType` == "REMOTE" (rippling.go:171,:259), BambooHR `locationType`+`isRemote` (bamboohr.go:93-94), Gem `job.locationType` (gem.go:94). Dates are ISO-8601 (Ashby publishedAt, Greenhouse updated_at), epoch seconds (Gem firstPublishedTsSec, gem.go:79), epoch milliseconds (Lever createdAt, lever.go:192), and relative English prose (Workday postedOn, workday.go:283). Each adapter must map into the closed enum / time.Time itself — the pattern already used for pay periods by `ashbyPeriod` (ashbyhq.go:475-483), `leverIntervals` (lever.go:293-299) and `jibeFrequencies` (jibe.go:123-130). Anything else pushes per-platform knowledge into internal/filter.go, where it cannot be unit-tested per adapter.

### Location fields are being flattened into strings that already lose structure the boards supplied
- impact: medium | effort: small | confidence: verified-in-code
- files: internal/services/smart_recruiters.go, internal/services/gem.go, internal/services/rippling.go, internal/services/workable.go

Three adapters join structured location components into a single string and lose the components: smart_recruiters.go:135-139 does `strings.Join([]string{city, region, country}, ",")` producing "Austin,TX,us" and ",,us" when city and region are absent; gem.go:175 does `Locations[0].Name + ", " + City + ", " + IsoCountry` producing "Remote, , US" (verified by running the adapter with a stub transport); rippling.go:244-265 joins multiple locations with "; " so a multi-location posting cannot be filtered per site. Meanwhile workable.go joins City/Region/Country (:166) while decoding but discarding `countryCode` (:94). Adding `city`/`region`/`country` (ISO code where available) and a `locations []string` field lets `--location` keep its current substring behaviour on the unchanged `location` string while a new `--country` can be exact. Note Gem takes only `Locations[0]` (gem.go:174-176), silently dropping every additional location on multi-site postings.

### Enrichment must not be allowed to make the already-failing nightly crawl worse
- impact: high | effort: small | confidence: verified-in-code
- files: .github/workflows/track_jobs.yml, internal/services/smart_recruiters.go, internal/services/gem.go, main.go

The nightly crawl already fails to finish 1,953 registered sources (counted from services.Builtin: greenhouse 647, ashby 418, workday 216, lever 161, rippling 128, jibe 71, workable 67, bamboohr 55, smartrecruiters 54, gem 51, peopleforce 37, jobvite 33, phenom 15) inside 75 minutes, reaching 473,385 postings from 1,772 companies. Tier 0 enrichment adds zero requests and zero bytes and is therefore safe to ship first and to leave on by default. Tier 1 adds ~850 MB of Greenhouse body to decode — CPU and memory, not requests, but it will still lengthen the run and should not be enabled in track_jobs.yml. Tier 2 would add on the order of 10^5–10^6 requests and must never be enabled in the nightly workflow. Two adjacent wins that *reduce* cost while enriching: setting `limit=100` on SmartRecruiters (smart_recruiters.go:92 sends no limit) cuts its request count roughly 10x, and fixing the Gem URL bug restores ~50x its current post-dedupe contribution for zero extra requests.

## Risks

- Every field list I attributed to Ashby, Workable, SmartRecruiters (customField), Phenom, Jibe and Rippling's detail endpoint comes from vendor or third-party documentation, not from a response this repo has ever decoded. This container has no outbound access to job boards, so none of it could be probed. A wrong field name produces a silently-empty column, and a wrong *type* produces a decode error that kills a whole tenant — exactly the failure mode documented at internal/services/jibe.go:95-101, where modelling one polymorphic field disabled nine large employers at once. Capture live bodies in Actions before writing any struct.
- Adding fields to a struct is not free of decode risk: job board APIs are polymorphic across tenants. docs/adding-a-source.md:129-133 states the rule ('Model only the fields you use'). Any newly modelled field whose type is uncertain should be json.RawMessage or `any` first, with a per-tenant survey, rather than a concrete type.
- Tier 1 (`--descriptions=same-request`) puts roughly 900 MB of Greenhouse HTML through the JSON decoder in a single process. That is a memory and CPU cost on top of a crawl that already misses its 75-minute deadline. It must not be enabled in .github/workflows/track_jobs.yml, and the description string must be released after pay extraction unless the caller asked to keep it.
- Tier 2 (per-posting detail fetches) is capable of adding 10^5–10^6 requests. Workday alone at 216 tenants with a page size of 20 becomes ~20x its current request count, and one tenant (FedEx, per main.go:536-540) publishes over 138,000 postings. Enabling this without a hard posting budget would both blow the time limit and constitute a real load increase on shared backends, which docs/architecture-roadmap.md:31-32 lists as a non-negotiable invariant.
- companies/uber.go exposes recruiter and hiring-manager names and email addresses (uber.go:38-45). Capturing personal data should be a deliberate, separately-reviewed decision, and such values must never reach manifests, logs, or metric labels (docs/architecture-roadmap.md:34-35).
- Filter.IsZero (filter.go:147-155) is a hand-maintained list that Apply short-circuits on. Adding filter fields without updating it makes the new flag silently return the entire crawl — a wrong-answer bug that produces no error and no log line.
- Emitting descriptions in the default NDJSON output would multiply stdout size by orders of magnitude across ~473k postings and would break the 'pipe it into jq' workflow the README advertises. Description text should be opt-in in the output even when it was free to obtain.
- The nightly Track Jobs workflow is already failing and jobs_record.txt already faces a ~35x coverage step change. Landing enrichment before the crawl completes reliably risks conflating two failure modes; the Tier 0 work is safe because it adds no network cost, but Tier 1 and Tier 2 should wait until a full crawl finishes within budget.
