# recon:ci-cd

## Summary

The nightly has far more ways to fail than the timeout, and the most dangerous one is new. jobs_record.gnuplot has never been executed in its current form: jobs_record.png was last regenerated at ec67e3a, while the script changed twice since (2a144ee added the datafile/outputfile indirection, 5e4a615 added the `$#` column guards, `linestyle 3`, and two all-NaN partial series) with no rebuild. That script runs at track_jobs.yml:193-195 — after the row is appended at :125 and before the commit at :213 — so any gnuplot error discards the day's row and reds the run. The same ordering hazard applies to the Python summarizer at :142-166, which hard-indexes six manifest keys with no try/except. Second: `git push origin HEAD:master` at :236 has no fetch/rebase/retry against a checkout up to six hours stale, and master took 8+ commits today. Third: the plausibility guard at :104 is bypassable — `[ "$POSTINGS" -lt 1000 ]` exits 2 on a non-numeric value, and because it sits in an `if` condition `set -e` does not fire, so the `||` evaluates false and the guard is skipped entirely; SOURCES is never validated at all and there is no coverage floor, so `--allow-partial` lets a five-minute blip become a permanent diamond. On question 2: recording a partial row is safe in gnuplot but NOT end to end. jobs_record.txt is measurably 2,046 rows of exactly 3 fields (550 carrying `?`), zero 4-column rows ever written, trailing newline present, no duplicate dates — so tonight is the first time a 4th column exists. The gnuplot guards are logically correct (gnuplot's `&&` short-circuits, so strcol(4) is never evaluated on 3-column rows) and every workflow consumer is column-count agnostic except one: track_jobs.yml:121 `printf '%s %s %s\n'` drops STATUS from the preview file, so a partial preview is drawn as a completed trend point — precisely what architecture-roadmap.md:25-27 forbids. A secondary design wart: jobs_record.gnuplot:44 also NaNs the source count on a partial row, breaking the lower panel's line directly above a caption at :141 asserting the source count was always recorded. Other real defects: the record date is computed twice from two clocks (step start at :57 vs crawl end at main.go:483) so they can straddle midnight; the `already recorded` grep at :71 locks a day to its first observation, making a partial row permanent; the concurrency group can queue a second six-hour crawl whose stale checkout also clears the guard; and all three workflows pin Node 20 actions, which runners already force onto Node 24 as of 2026-06-16 and which stop working on 2026-09-16. For tonight specifically, the highest-leverage single change is `--concurrency=32`: the nightly currently inherits `min(32, max(8, NumCPU*4))` = 16 on a 4-vCPU runner while per-service limits stay at 2-4, so doubling source fan-out adds zero pressure on any board. The 350m budget also has under ten minutes of true slack because checkout, setup-go with check-latest, `apt-get install gnuplot` (the full X/Qt metapackage, not gnuplot-nox) and `go build` all precede the crawl. On sharding: the roadmap's plan/matrix/merge shape is right, but measurement shows it cannot parallelise the bottleneck — 11 of 13 platforms are single shared hosts (greenhouse 647 on boards-api.greenhouse.io, ashby 418 on api.ashbyhq.com, lever 161, rippling 128, jibe 71, workable 67, bamboohr 55, smartrecruiters 54, gem 51, peopleforce 37, jobvite 33) that must each stay whole in one shard, because every shard is a separate process with its own httpx.hostLimiter and splitting a shared host multiplies its concurrency by the shard count. Only workday's 216 tenant hosts and phenom's 15 are genuinely splittable. Sharding therefore buys fault isolation, per-shard budgets and a merge-time integrity proof, not wall-clock. The merge must union `internal.DedupeKey` values rather than sum per-shard totals, which requires extracting that key from internal/filter.go:253-258, adding a `ServiceKey` field to services.Source, adding `services.Resolve` to fail closed on unknown refs, and extending crawlManifest to schema 2 with plan_id/shard_index/commit/complete. The merge job must be gated on `if: ${{ !cancelled() }}` — with plain `needs`, one failed shard skips it, and a skipped job is not a failure. Finally, ci.yml is decent (race, shuffle, gofmt, mod-tidy, staticcheck pinned to 2025.1.1, minimal permissions) but pins govulncheck to `@latest`, has no OS or Go-version matrix, no CGO_ENABLED=0 portability assertion, no per-job timeout, and — most relevant here — no gnuplot render check, which is exactly the gap that let the untested chart change reach the nightly.

## Findings

### jobs_record.gnuplot in its current form has NEVER been executed — the plot step is an unproven failure point that runs after the row is appended but before the commit
- impact: critical | effort: small | confidence: verified-in-code
- files: jobs_record.gnuplot, .github/workflows/track_jobs.yml, jobs_record.png

Verified from git history. `git log --oneline -- jobs_record.png` shows the PNG was last regenerated in ec67e3a. `git log --oneline -- jobs_record.gnuplot` shows the script changed TWICE since: 2a144ee (added the `datafile`/`outputfile` indirection, jobs_record.gnuplot:47-50, 120-123, 146-148) and 5e4a615 (added `$#` column guards at :42-45, `set style line 3 ... pointtype 13` at :67, and two brand-new all-NaN series `@partial_postings` / `@partial_sources` at :123 and :148). Neither commit rebuilt jobs_record.png, so there is no proof-of-run in the repo for any of it. Step ordering in track_jobs.yml makes this critical: the row is appended to the worktree at :125, then `Summarize crawl diagnostics` (:134-180), then `Upload` (:182-191), then `Regenerate historical plot` (:193-195, `gnuplot jobs_record.gnuplot`), and ONLY THEN `Commit and push` (:213-236). Any non-zero exit from gnuplot (or from the Python summarizer) kills the job before the commit, and the day's row — which exists only in the runner's worktree — is discarded. The specific unproven constructs: (a) `$#` is documented as a gnuplot pseudocolumn holding the number of columns in the current record, present in the 5.5/6.0 docs (gnuplot.info/docs_6.0/loc9474.html); ubuntu-24.04 ships gnuplot 6.0.0+dfsg1-1ubuntu3, so it should resolve on ubuntu-latest, but not on gnuplot <= 5.2 that a contributor may have. (b) gnuplot's `&&` is documented to short-circuit like C, so `$# >= 4 && strcol(4) eq "partial"` does NOT evaluate strcol(4) on today's 3-column rows — that part is sound. (c) `datafile using 1:@partial_postings with points linestyle 3` evaluates to NaN for every one of the 2,046 current rows; gnuplot normally emits `Warning: Skipping data file with no valid points` (non-fatal) when sibling plots in the same command have valid points, but I could NOT verify this — gnuplot is not installable in this container. This is the single highest-probability way tonight's run still ends red.

### `git push origin HEAD:master` has no fetch/rebase/retry and races a master that received 8+ commits today
- impact: critical | effort: small | confidence: verified-in-code
- files: .github/workflows/track_jobs.yml, .gitignore

track_jobs.yml:236 is a bare `git push origin HEAD:master` against a checkout taken up to ~6 hours earlier (:34). There is no `git fetch` / `git pull --rebase` / retry loop. Any commit landing on master during the 350-minute crawl produces a non-fast-forward rejection, the step fails under `set -euo pipefail` (:221), and the appended row is lost entirely — it was never committed anywhere. `git log --oneline -15` shows 5e4a615, 6549410, 2a144ee, 970d20e, 8a48069 all authored on 2026-07-25/26, so master is actively busy. Note also that `git add jobs_record.txt jobs_record.png` (:226) is explicit, so the untracked total.txt / crawl-manifest.json / jobs_record-preview.* are correctly excluded (they are NOT in .gitignore, which only covers /job-hunter-toolkit, /cmd, *.exe, *.test, *.out, coverage.*).

### The plausibility guard is silently bypassed by any non-numeric or multi-line POSTINGS value
- impact: high | effort: small | confidence: verified-in-code
- files: .github/workflows/track_jobs.yml

track_jobs.yml:104 is `if [ -z "$POSTINGS" ] || [ "$POSTINGS" -lt 1000 ]; then ... exit 1; fi`. If POSTINGS is non-numeric (or multi-line), `[ "$POSTINGS" -lt 1000 ]` exits 2 with `integer expression expected`. Because the test is an `if` CONDITION, `set -e` (:55) does not fire on it, and `||` with a non-zero right operand evaluates false — so the guard body never runs, the garbage row is appended at :125 and committed. The guard is meant to be the last line of defence for a file the project calls its longest-running artifact. Correct form: `[[ "$POSTINGS" =~ ^[0-9]+$ ]] || { echo '::error::...'; exit 1; }`. Related: `SOURCES` (:101) is never validated at all — no numeric check, no floor, no comparison against the manifest's planned source count.

### awk reads every line of total.txt, not the first, so any future stdout write corrupts POSTINGS/SOURCES/STATUS and breaks GITHUB_OUTPUT
- impact: medium | effort: small | confidence: verified-in-code
- files: .github/workflows/track_jobs.yml, main.go

track_jobs.yml:100-102 use `awk '{print $2}' total.txt` etc. with no `NR==1`. total.txt is one line today (main.go:482-483 is the only stdout write, and `grep -rn 'fmt.Print|os.Stdout|println(' internal/` returns nothing outside tests — verified). But any future stdout emission — a cobra deprecation notice, a panic trace, a second row — makes these variables multi-line. Two consequences: the numeric guard is bypassed (see previous finding), and `echo "postings=$POSTINGS" >> "$GITHUB_OUTPUT"` at :130-132 writes a multi-line value with no heredoc delimiter, which GitHub rejects as malformed output. Fix: `awk 'NR==1{print $2}'` plus `[ "$(wc -l < total.txt)" -eq 1 ] || exit 1`.

### The preview path drops the STATUS column, so a partial preview renders as a completed trend point — the exact failure the design forbids
- impact: high | effort: small | confidence: verified-in-code
- files: .github/workflows/track_jobs.yml, jobs_record.gnuplot

track_jobs.yml:121 is `printf '%s %s %s\n' "$RECORD_DATE" "$POSTINGS" "$SOURCES" >> jobs_record-preview.txt` — three fields, no `$STATUS`, even though STATUS was just extracted at :102 and validated at :108-114. jobs_record.gnuplot:42-45 keys the entire partial/complete distinction on column 4, so a partial preview row satisfies `$# >= 4` = false and is drawn by `@postings` as a normal point: it joins the completed trend line AND fills its area. That directly violates docs/architecture-roadmap.md:25-27 ('A partial crawl is never recorded or graphed as complete') and docs/jobs-record.md:13-18. The production path at :125 (`cat total.txt >> jobs_record.txt`) is correct — it copies all four fields. Fix: `printf '%s %s %s %s\n' ... "$STATUS"`.

### The record date is computed twice from two different clocks, so the duplicate guard can check one date while the file records another
- impact: medium | effort: small | confidence: verified-in-code
- files: .github/workflows/track_jobs.yml, main.go

track_jobs.yml:57 computes `RECORD_DATE=$(date "+%m/%d/%y")` at STEP START. That value drives the 'already recorded' grep (:71), the preview row (:121), and the commit message (:235). But the row actually appended at :125 carries the date `total` printed at CRAWL END: main.go:483 `time.Now().Format("01/02/06")`. With `--timeout=350m` these can differ by a full day for any manual dispatch after ~18:00 UTC or any run crossing midnight. Result: the duplicate guard clears for date D while the file gains a row for D+1 — producing a duplicate row for D+1 on the next scheduled run and a permanent hole at D, plus a commit message naming the wrong day. The scheduled 09:00 UTC run (:5) is safe today only because 09:00 + ~5h55m stays inside the same UTC day. Fix: add a `total --date=` flag, or re-derive RECORD_DATE from `awk 'NR==1{print $1}' total.txt` after the crawl and use that everywhere.

### The 'already recorded' skip makes a partial row permanent for that day — a later complete crawl can never supersede it
- impact: medium | effort: small | confidence: verified-in-code
- files: .github/workflows/track_jobs.yml

track_jobs.yml:71-76: `if [ "$PREVIEW" != "true" ] && grep -q "^$RECORD_DATE " jobs_record.txt; then ... recorded=false; exit 0; fi`. The grep is column-count agnostic, so it matches a 3-column OR 4-column row equally. Once a `partial` row is committed for date D, every re-run and manual dispatch on D short-circuits before the crawl, so the day is locked to the worse observation. Given the workflow was just switched to `--allow-partial`, this converts every deadline day into a permanent diamond even if a re-run would finish. Fix: when the existing row for D ends in `partial` and the new crawl is `complete`, rewrite the row in place (`awk -v d=$D '$1 != d' jobs_record.txt > tmp && cat total.txt >> tmp && mv tmp jobs_record.txt`) instead of skipping.

### The Python summarizer runs before the commit and hard-indexes six manifest keys, so a schema change reds the job and drops the day's row
- impact: high | effort: small | confidence: verified-in-code
- files: .github/workflows/track_jobs.yml, crawl_report.go

track_jobs.yml:142-166 does `manifest["duration_ms"]`, `manifest["source_counts"]`, `manifest["sources"]`, `manifest['status']`, `manifest['postings']`, `manifest['companies']` with no `.get()` and no try/except, and the step is `if: always()` (:135) — but 'always' only means it runs, not that its failure is tolerated. It sits between the append (:125) and the commit (:213), so any KeyError or malformed JSON destroys the run and the row. crawl_report.go:13 pins `crawlManifestSchemaVersion = 1` today, but architecture-roadmap.md:58-68 explicitly plans to extend the manifest. Fix: `continue-on-error: true` on this step, or move `Commit and push` immediately after the guard.

### The nightly runs at concurrency 16, not 32 — the single highest-leverage one-line change for finishing the crawl
- impact: high | effort: small | confidence: verified-in-code
- files: .github/workflows/track_jobs.yml, internal/all.go, internal/httpx/httpx.go

track_jobs.yml:84-90 never passes `--concurrency`, so it takes the default from main.go:52-53 -> internal/all.go:27: `DefaultConcurrency = min(32, max(8, runtime.NumCPU()*4))`. A GitHub-hosted standard Linux runner has 4 vCPU, giving `min(32, max(8, 16)) = 16` concurrent sources for ~1,890 sources. Raising it to `--concurrency=32` doubles source-level fan-out WITHOUT increasing pressure on any single service: internal/httpx/httpx.go:242-281 caps per-service-key concurrency independently (workable 2, peopleforce 2, greenhouse/lever/rippling/gem/smartrecruiters/bamboohr/jibe 4, everything else 4 by exact host), so politeness is preserved and only cross-service parallelism increases. This satisfies architecture-roadmap.md:31 ('Higher concurrency ... not permission to increase pressure on a shared service').

### The 350m budget leaves under 10 minutes of real slack because apt-get/setup-go/build all run before the crawl
- impact: high | effort: small | confidence: verified-in-code
- files: .github/workflows/track_jobs.yml, internal/httpx/httpx.go

track_jobs.yml:31 sets `timeout-minutes: 360`, which is exactly GitHub's 6-hour per-job ceiling — so the workflow timeout and GitHub's own hard kill coincide with no margin. Before the crawl starts the job runs checkout (:34), setup-go with `check-latest: true` (:37-40, forces a toolchain download rather than using the preinstalled Go), `sudo apt-get update && sudo apt-get install -y gnuplot` (:42-45 — the full `gnuplot` metapackage pulls the Qt/X11 dependency chain; `gnuplot-nox` is the right package for a headless PNG render), and `go build` (:48). That is typically 2-5 minutes, so the crawl ends around T+352..355 and everything after it — Python summary, artifact upload, gnuplot, commit, push — must fit in the remainder. There is also no step-level `timeout-minutes` on the count step, so a crawl that fails to unwind consumes the entire job budget. Note the unwind path itself is sound: every wait in httpx is context-aware (`sleep(ctx, d)` at httpx.go:730-744, used by `limitState.wait` :320 and the retry loop :578), and `backoff` clamps Retry-After to `maxDelay` = 30s (httpx.go:33-49, 629-631), so the observed peopleforce Retry-After of 3510s is bounded to 30s and cannot hang the crawl. Fixes: `gnuplot-nox`, move the apt install after the crawl, drop `--timeout` to 300m, add `timeout-minutes: 320` on the count step.

### All three workflows pin Node 20 actions; runners defaulted to Node 24 on 2026-06-16 and Node 20 is removed 2026-09-16
- impact: high | effort: small | confidence: documented
- files: .github/workflows/track_jobs.yml, .github/workflows/ci.yml, .github/workflows/source_health.yml

`actions/checkout@v4`, `actions/setup-go@v5` and `actions/upload-artifact@v4` all declare `runs.using: node20`. Per GitHub's changelog (github.blog/changelog/2025-09-19-deprecation-of-node-20-on-github-actions-runners/), runners began using Node 24 by default on 2026-06-16 and Node 20 is removed on 2026-09-16 — so as of today (2026-07-26) these actions are already being executed on Node 24 and emit deprecation warnings, and they will stop working outright in ~7 weeks. Affected lines: track_jobs.yml:34, 37, 184, 206; ci.yml:24, 27, 64, 67, 81, 84; source_health.yml:26, 28, 92. Replacements: `actions/checkout@v5` (v6 also available), `actions/setup-go@v6` (v6 is the node24 edition, requires runner >= 2.327.1 which GitHub-hosted satisfies), `actions/upload-artifact@v6` (v5 only had preliminary node24 support and still defaulted to node20; v6 declares `runs.using: node24`). Worth pinning to commit SHAs at the same time. I am confident about setup-go v6 and upload-artifact v6; I did not find an authoritative page stating which checkout major first declared node24, so verify checkout v5 vs v6 before bumping.

### The concurrency group can queue a second full-day crawl and lets two runs both pass the duplicate guard
- impact: medium | effort: small | confidence: verified-in-code
- files: .github/workflows/track_jobs.yml

track_jobs.yml:20-22 sets `group: track-jobs, cancel-in-progress: false`. With a job that can occupy up to 6 hours, a manual dispatch during a scheduled run queues rather than being rejected, and GitHub keeps only ONE pending run per group, so a third dispatch is silently cancelled. Worse for integrity: the queued run checks out master AFTER the running job's crawl started but BEFORE its commit lands, so both runs see a jobs_record.txt without today's row, both clear the grep at :71, both crawl, and both try to append a row for the same date. The grep guard is a check-then-act race that cannot protect against this because the check happens ~6 hours before the write. Mitigation: keep `cancel-in-progress: false` but make the merge/commit step re-check for the date immediately before appending, after a `git pull --rebase`.

### There is no coverage floor on a partial row — a crawl that dies after 30 sources is recorded as long as postings >= 1000
- impact: high | effort: small | confidence: verified-in-code
- files: .github/workflows/track_jobs.yml, crawl_report.go, internal/services/observe.go

track_jobs.yml:104-114 checks only `POSTINGS >= 1000` and `STATUS in {complete, partial}`. crawl-manifest.json already carries everything needed for a real integrity check: crawl_report.go:15-26 exposes `source_counts` (a map over the six statuses defined at internal/services/observe.go:17-24: planned/running/complete/failed/truncated/stopped), `postings`, `companies`, and the full per-source array. A partial row should additionally require something like `(complete + failed) / len(sources) >= 0.90` and `postings >= 0.5 * <last recorded postings>`, both computable in the existing Python step. Without it, `--allow-partial` converts a 5-minute network blip into a permanent diamond on a 6-year series.

### source_health.yml omits `set -e`, so a crashed health binary produces a green run with no data
- impact: medium | effort: small | confidence: verified-in-code
- files: .github/workflows/source_health.yml, main.go

source_health.yml:39 is `set -uo pipefail` — deliberately without `-e`. At :42 `./job-hunter-toolkit health --json --timeout=45m > health.json 2> health-summary.txt` can fail and leave health.json empty or truncated (main.go:604-610 encodes the whole array at the end, so a crash yields nothing). The heredoc Python at :46-76 then raises on `json.load`, and the `TOTAL=$(python3 -c ...)` / `FAILED=$(...)` at :80-81 also raise, leaving both empty. `[ "$TOTAL" -gt 0 ]` at :85 then exits 2 with 'integer expression expected' — but it is an `if` condition and `-e` is off, so the branch is false and the step exits 0. The workflow reports success having checked nothing. Fix: `set -euo pipefail` plus an explicit `[ -s health.json ]` assertion.

### source_health's 35% failure alarm cannot distinguish 'adapter broken' from 'deadline reached'
- impact: medium | effort: medium | confidence: verified-in-code
- files: .github/workflows/source_health.yml, main.go, internal/services/observe.go

main.go:695-725 (`checkSources`) records any error from `source.Jobs(ctx, client)` into `health.Error`, and a source with an error and zero postings becomes `statusFailed` (:718-725). When the 45-minute deadline at source_health.yml:42 fires, every not-yet-reached and in-flight source gets `context deadline exceeded` and is classified `failed`. source_health.yml:85-87 then fails the run with `::error::N/M sources failed, which suggests an adapter is broken rather than boards being retired` — a materially misleading message. Unlike `total`, `health` does not use `services.Observe` (internal/services/observe.go:48), writes no manifest, and has no `--allow-partial` equivalent, so there is no way to tell the two cases apart from the artifact. Given the full crawl now exceeds 75 minutes, a 45-minute health cap over ~1,890 sources is not obviously safe even with the 100-posting cap at main.go:534-541.

### Sharding cannot parallelise the crawl's real bottleneck: 11 of 13 platforms are single shared hosts that must stay in ONE shard
- impact: high | effort: medium | confidence: verified-in-code

### Sharded crawl: exact workflow YAML shape, and why the merge job must not be `needs`-skipped
- impact: high | effort: medium | confidence: inferred
- files: .github/workflows/track_jobs.yml, docs/architecture-roadmap.md, internal/filter.go

Three jobs replacing the single `report_total_jobs`. `plan`: checkout/setup-go/build, `./job-hunter-toolkit plan --shards=8 --output=plan.json --github-matrix=matrix.json`, `outputs.shards: ${{ steps.plan.outputs.shards }}`, upload plan.json as artifact `crawl-plan` with `if-no-files-found: error`. `crawl`: `needs: plan`, `timeout-minutes: 90`, `strategy: { fail-fast: false, max-parallel: 4, matrix: { shard: ${{ fromJSON(needs.plan.outputs.shards) }} } }` (fail-fast:false and a conservative max-parallel are both mandated by architecture-roadmap.md:131-133), download `crawl-plan`, run `crawl --plan=plan.json --shard=${{ matrix.shard }} --timeout=75m --allow-partial`, then `uses: actions/upload-artifact` with `if: always()` and `if-no-files-found: error` so a failing shard still uploads its manifest. `merge`: `needs: [plan, crawl]` plus **`if: ${{ !cancelled() }}`** — this is the critical detail. With plain `needs`, a single failed shard SKIPS the merge job, and a skipped job is not a failure: the run would be reported without ever explaining which sources were missed. `!cancelled()` forces the merge to run, download `pattern: crawl-shard-*` with `merge-multiple: true`, and let the `merge` command fail closed with a precise 'shard 5 missing / sources X,Y,Z uncovered' message. The merge job is the only one needing `permissions: contents: write`; plan and crawl take `contents: read`. Move the `gnuplot-nox` install and the commit/push into `merge` only. Global dedupe survives because merge unions DedupeKeys across all shards before counting — per-shard totals must never be summed (architecture-roadmap.md:127-129: the same posting URL can appear through two integrations, and internal/filter.go:253 keys on exactly that URL).
