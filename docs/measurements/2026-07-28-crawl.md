# Crawl measurement, 2026-07-28

First end-to-end measurement of the crawler against live job boards after #29's
throughput fixes and this branch's coverage work. Every number here was produced
by one run, not extrapolated.

## Result

```
$ job-hunter-toolkit total --timeout=12m --allow-partial --concurrency=24 --manifest=...
07/28/26 780489 3462 partial
```

| | 07/26 baseline | 07/28 |
| --- | ---: | ---: |
| postings | 473,404 | **780,489** |
| companies | 1,772 | **3,462** |
| sources registered | 2,211 | 3,685 |
| wall clock | **unfinished at 350 min** | **12 min** |

`source_counts`: 3,675 complete, 8 failed, 2 truncated. Every one of the 3,685
sources reached a terminal state inside the budget. The run is labelled
`partial` because of the two truncated sources, not because it ran out of time.

The nightly is currently budgeted 330 minutes for this work. That is roughly
**27x more than it needs**, which matters directly: GitHub Actions minutes are
the project's main running cost, and the crawl is nearly all of them.

## Cost per platform

Total source-time was 8,362 source-seconds against 720 seconds of wall clock at
concurrency 24 — about 48% utilisation, and the gap is the shared-backend tail
described in `internal/httpx`'s SMB policy comment.

| platform | source-seconds | postings | sources | **s / 1k postings** |
| --- | ---: | ---: | ---: | ---: |
| greenhouse | 195 | 42,010 | 646 | **4.6** |
| smartrecruiters | 240 | 44,414 | 54 | 5.4 |
| ashby | 76 | 12,772 | 417 | 5.9 |
| jibe | 1,246 | 202,926 | 125 | 6.1 |
| lever | 81 | 9,897 | 161 | 8.2 |
| workday | 1,802 | 174,929 | 210 | 10.3 |
| oraclecloud | 1,042 | 91,030 | 30 | 11.4 |
| successfactors | 232 | 18,375 | 30 | 12.6 |
| phenom | 310 | 22,859 | 15 | 13.6 |
| pinpoint | 143 | 6,406 | 118 | 22.3 |
| recruitee | 272 | 9,830 | 492 | 27.6 |
| **personio** | **2,484** | 11,920 | 970 | **208.4** |

Personio costs 45x more per posting than Greenhouse and is 30% of all
source-time for 1.5% of the postings. Nothing is wrong with the adapter: 970
tenants share one limiter key at four concurrent, so the platform is ~243
sequential rounds regardless of idle workers. It is the clearest possible
argument for scheduling by measured cost rather than by source count, and for
sharding by affinity rather than evenly.

## What this does and does not settle

**Settles:** the crawl finishes. `docs/crawl-budget-model.md` was written
expecting the opposite, and its migration steps stand — bounding a run is still
what makes the browser and daemon surfaces work, and staleness-ordering is still
what makes a bounded run spend its budget well. But the urgency is now cost and
portability, not deadline failure.

**Does not settle:** this ran on a 4-vCPU container with one IP, not on a GitHub
runner, and concurrency was 24 rather than the default 64. A runner may differ
in DNS, egress shaping and TLS throughput. Re-measure there before changing the
nightly's budget.

# Second measurement, same day, 8,145 sources

Taken after the registry grew from 3,685 to 8,145 sources with Breezy,
BrassRing, and the promoted Oracle Cloud, Teamtailor, Personio, SuccessFactors,
Recruitee and Pinpoint tenants.

```
$ job-hunter-toolkit total --timeout=40m --allow-partial --concurrency=32 --manifest=...
07/28/26 1236756 7931 complete
```

| | 07/26 baseline | 07/28 first | **07/28 second** |
| --- | ---: | ---: | ---: |
| postings | 473,404 | 780,489 | **1,236,756** |
| companies | 1,772 | 3,462 | **7,931** |
| sources | 2,211 | 3,685 | **8,145** |
| wall clock | unfinished at 350 min | 720 s | **945 s** |
| status | partial | partial | **complete** |

**This is the first crawl this project has recorded as `complete`.** 8,136 of
8,145 sources finished; 9 failed. Against the baseline it is 2.6x the postings
from 4.5x the companies in about 1/22nd the wall clock.

Note the shape of the growth: sources rose 121% and wall clock rose 31%. The
crawl is bound by its slowest shared backends, not by source count, which is why
adding four thousand sources cost four minutes.

## Cost per platform, second measurement

Total source-time 15,960 seconds against 945 seconds of wall clock at
concurrency 32 — about 53% utilisation.

| platform | source-seconds | postings | sources | **s / 1k postings** |
| --- | ---: | ---: | ---: | ---: |
| smartrecruiters | 252 | 44,407 | 54 | **5.7** |
| brassring | 394 | 63,812 | 33 | **6.2** |
| jibe | 3,028 | 414,318 | 247 | 7.3 |
| oraclecloud | 2,606 | 269,196 | 1,203 | 9.7 |
| workday | 1,731 | 165,764 | 210 | 10.4 |
| successfactors | 2,162 | 98,284 | 717 | 22.0 |
| recruitee | 285 | 9,832 | 492 | 29.0 |
| breezy | 1,532 | 36,009 | 1,492 | 42.5 |
| personio | 785 | 11,920 | 970 | 65.8 |
| **teamtailor** | 2,333 | 24,342 | 988 | **95.9** |

The enterprise lanes carry the corpus and are cheap: Jibe alone is 414,318
postings at 7.3 s/1k, and BrassRing returns 63,812 postings from 33 sources at
6.2 — the best ratio in the registry.

The SMB lanes are the opposite. Teamtailor, Personio and Breezy are 3,450
sources between them, 30% of all source-time, for 72,271 postings — 5.8% of the
corpus. Nothing is wrong with those adapters; each tenant is one small board
behind a shared limiter key. It is simply what a budget-aware scheduler must
know, and the argument for ordering work by measured cost rather than by source
count (docs/crawl-budget-model.md).

## What this settles for the nightly

`track_jobs.yml` budgets **330 minutes** for work that takes **16**. That is
about 21x oversized, on a workflow that is nearly all of this project's Actions
spend.

The caveat from the first measurement still stands and is the reason this has
not been cut yet: this ran on a 4-vCPU container with one IP at concurrency 32,
not on a GitHub runner at the default 64. Re-measure there before changing the
budget. The right first step is to record the runner's own wall clock from a
normal nightly run, which the crawl manifest already reports.
